# FRP 全套程序 需求收集文档

> 项目：准商业级 FRP 全套程序（服务端、客户端、管理端、官网）
> 对标：https://www.chmlfrp.net/
> 文档：CQFISH&喵酱出品
> 创建日期：2026-08-15

## 问答记录

### 第 1 轮：整体定位

**提问：** 项目要达到的商业化程度是哪种？

- A. 完整商业化对标：完整复刻 ChmlFrp 模式，含免费+付费套餐、支付/订单、每日签到、会员等级、节点权限分级、开放 API
- B. 准商业核心版：有用户注册登录、隧道管理、多节点管理、套餐限制（限速/隧道数），先不做真实支付，用虚拟积分/签到代替，后续再接支付
- C. 核心功能优先：先跑通服务端+客户端+管理面板+官网，商业化功能留到第二阶段

**主人回答：** B

**结论：**
- 定位为准商业核心版
- 包含：用户注册登录、隧道管理、多节点管理、套餐限制（限速/隧道数）
- 不做真实支付，采用虚拟积分/签到机制，后续可平滑升级到完整商业化

### 第 2 轮：技术栈路线

**提问：** FRP 服务端和客户端内核如何实现？（主人反问：能不能用 Python？）

**说明：**
- Python 全栈自研可行（asyncio + uvloop），但需自研协议、无法复用 frp 内核、高并发转发性能低于 Go
- 给出了三条路线：A 全栈 Python 自研 / B 混合架构（Go 内核 + Python 管理面）/ C 全栈 Python 但协议兼容设计

**主人回答：** B

**结论（技术栈定为）：**
- 服务端/客户端内核：Go，基于 fatedier/frp 二次开发（Apache 2.0，可商用）
- 管理端：Python FastAPI + 前端面板
- 官网：Python（FastAPI 渲染 或 静态站）
- 数据库、消息队列等中间件待定

### 第 19 轮：整体技术方案（轻量版）

**提问：** 方案选择？（原方案1 FastAPI 现代栈 / 方案2 Django / 方案3 轻量），主人要求"极度轻量"

**主人回答：** 极度轻量方案，数据库用 SQLite（WAL），保留一个轻量 Redis

**结论（技术方案定稿）：**
- 面板后端：FastAPI 单进程（uvicorn 单 worker）
- 数据库：SQLite（WAL 模式）
- 缓存/会话：轻量 Redis（单实例，用于会话/缓存/实时状态）
- 异步任务：asyncio 后台任务（不引入 Celery/消息队列）
- 面板前端：Vue3 + Naive UI，构建为静态文件部署
- 官网：FastAPI + Jinja2 服务端渲染
- 内核：Go frps（二开：控制通道 API + 用户鉴权 + 限速联动）+ frpc Windows 10/11 版
- 部署：Docker Compose（面板 + frps + Redis 三容器，SQLite 数据挂载卷）
- 整体内存占用目标 200MB 以内
